# kns-report — суточный отчёт КНС-1

Утилита командной строки собирает почасовой отчёт по станции: уровень в резервуаре, откачанный
объём, моточасы и пуски насосов, срабатывания тревог. Данные берутся из InfluxDB 2 (запрос Flux
через HTTP API) или прямо с OPC UA-сервера ПЛК или эмулятора. История на сервере OPC UA не нужна:
утилита сама опрашивает теги N минут. Результат — CSV для обработки и оформленный XLSX для людей.

Теги — из модели флагмана (проект 02): файлы `kns_report/data/scada_tags.csv` и
`scada_alarms.csv` — вывод генератора iolistgen по перечню сигналов КНС-1, копия
`schema/source/` (совпадение проверяет тест, чтобы копии не разошлись).

## Установка

```bash
python -m pip install -e report            # из корня репозитория; команда kns-report
python -m pip install -e "report[tz]"      # плюс tzdata: имена поясов IANA (--tz Europe/Moscow) на Windows
```

Нужен Python 3.11+. Зависимости: openpyxl, asyncua. К InfluxDB утилита обращается стандартной
библиотекой (urllib), клиент InfluxDB не нужен.

## Запуск

```bash
# сутки из InfluxDB стенда; порт InfluxDB на 127.0.0.1 открывает docker-compose.dev.yml (make up DEV=1).
# Из .env берутся INFLUX_ORG, INFLUX_BUCKET, INFLUX_PORT и токен: INFLUX_TOKEN, если задан,
# иначе INFLUX_ADMIN_TOKEN стенда (с предупреждением — см. «Безопасность»)
kns-report influx --date 2026-10-15 --env-file .env
kns-report influx --env-file .env                        # без --date — вчерашние сутки

# выборка с OPC UA-сервера эмулятора или CODESYS Control: 10 минут с шагом 1 с
kns-report opcua --endpoint opc.tcp://localhost:4840 --minutes 10 --interval 1 --save-samples build/samples.jsonl

# то же с учётной записью и шифрованием (пароль — только в переменной OPCUA_PASSWORD)
kns-report opcua --user report \
  --security "Basic256Sha256,SignAndEncrypt,certs/report.der,certs/report_key.pem,certs/plc.der"

# повтор отчёта из сохранённых данных
kns-report file build/samples.jsonl
kns-report file build/raw.csv --date 2026-10-15          # ответ InfluxDB, сохранённый через --save-raw
```

Результат по умолчанию — в `build/reports/` (каталог `build/` в git не попадает):

| Файл | Что внутри |
|---|---|
| `kns1_daily_2026-10-15.csv` | почасовая таблица (24 строки) |
| `kns1_daily_2026-10-15_alarms.csv` | срабатывания тревог: время, код, приоритет, текст |
| `kns1_daily_2026-10-15.xlsx` | листы «Отчёт», «Сводка», «Тревоги», «Графики» |

Для неполных периодов (выборка OPC UA) имя — `kns1_report_<дата>_<ЧЧММ>-<ЧЧММ>`.

Общие опции: `--config my.toml` (настройки поверх `kns_report/default_config.toml`), `--tz`,
`--out-dir`, `--formats csv,xlsx`, `--catalog schema/telemetry_catalog.csv`, `--tags-csv`,
`--alarms-csv`, `-v`. Полный список — `kns-report <режим> --help`.

## Колонки отчёта

CSV: UTF-8 без BOM, разделитель `;`, десятичная точка, пустая ячейка — нет данных за час.

| Колонка CSV | Лист «Отчёт» | Единицы | Как считается |
|---|---|---|---|
| `hour_start` | Час | ISO 8601 с поясом | начало местного часа |
| `level_min_m`, `level_avg_m`, `level_max_m` | Уровень мин., ср., макс. | м | LT101: минимум, средневзвешенное по времени, максимум |
| `volume_m3` | Откачано | м³ | интеграл расхода FT202 (м³/ч × ч) |
| `p101_run_h`, `p102_run_h`, `p103_run_h` | Н1…Н3: работа | ч | приращение счётчика наработки ПЛК `RunTime`; без счётчика — время с `Running = TRUE` |
| `p101_starts`, `p102_starts`, `p103_starts` | Н1…Н3: пуски | шт. | приращение счётчика `Starts`; без счётчика — фронты `Running` |
| `alarms_total` | Тревог всего | шт. | срабатывания тревог за час |
| `alarms_high`, `alarms_medium`, `alarms_low` | из них High, Medium, Low | шт. | по приоритету из `scada_alarms.csv` (Critical считается как High) |
| `data_coverage_pct` | Полнота данных | % | доля часа, покрытая данными уровня и расхода (меньшая из двух) |

Лист «Отчёт» в XLSX: заголовок станции и периода, строка «Сутки» с итогами, закреплённая шапка,
форматы чисел (уровень `0.00`, объём `0.0`, часы `0.00`, полнота `0%`). Условное форматирование:

- уровень макс. ≥ HH (4,0 м) — красная заливка, ≥ H (3,5 м) — жёлтая; уровень мин. ≤ LL (0,5 м) —
  красная, ≤ L (0,8 м) — жёлтая. Уставки берутся из `scada_tags.csv` (колонки `alarm_*` тега LT101);
- тревог за час больше нуля — розовая заливка, тревоги High — красная с белым шрифтом;
- полнота данных меньше 95 % — жёлтая;
- объём — гистограмма в ячейке.

Остальные листы: «Сводка» — итоги за период, наработка и пуски по насосам с показаниями
счётчиков на конец периода и методом расчёта, замечания к данным; «Тревоги» — список срабатываний
с фильтром; «Графики» — уровень (мин., ср., макс.), объём по часам, работа насосов (накопительно),
тревоги по приоритетам.

## Методика

- **Удержание значения.** Значение действует от своей отметки времени до следующей, но не дольше
  `analog_max_gap` (10 мин) для аналоговых сигналов и `discrete_max_gap` (2 ч) для дискретных.
  Это соответствует публикации «по изменению плюс периодически»: дискретный сигнал может долго не
  меняться. Дальше разрыва час считается без данных, и это видно в колонке полноты.
- **Граница данных.** Последнее значение не тянется дальше конца выборки OPC UA или текущего
  момента: отчёт за сегодняшние сутки не «досчитывает» будущее.
- **Счётчики.** Уменьшение счётчика считается сбросом (приращение = новое значение). Колебание
  наработки в пределах 0,001 ч — погрешность `REAL`, не сброс. Приращение наработки между двумя
  точками делится между часами пропорционально времени, пуск относится к часу, где счётчик вырос.
- **Тревоги.** Из InfluxDB — события срабатывания (`reason = Activated`) из топиков
  `.../<device>/alarm/<SUFFIX>`. При опросе OPC UA — фронты битов слов `<DEV>.AlmActive`
  (бит = слот тревоги, `id = dev_no · 10 + слот`). Тревога, активная до начала периода, новым
  срабатыванием не считается.
- **Запрос к InfluxDB** начинается раньше суток на `max(analog_max_gap, discrete_max_gap)`: так
  известны значения на 00:00.

## Схема данных в InfluxDB

Модель хранения — [docs/data_schema.md](../docs/data_schema.md), раздел 7. Бакет сырых данных
`kns_raw`, организация `vodokanal`. Телеметрия: measurement `telemetry`, поле `value`, теги из
сегментов топика `vodokanal/kns1/station/<device>/<metric>` — `site`, `area`, `unit`, `device`,
`metric` — и тег пути данных `source`. Отчёт берёт `source = mqtt` (значения, опубликованные ПЛК)
и отбрасывает точки с `quality = bad`: запрос сводит поля `value` и `quality` в строку (`pivot`).
Для данных, собранных Telegraf по OPC UA, в настройках задаётся `source = "opcua"` и
`quality_field = ""`. Метрики для тегов отчёта — по `schema/telemetry_catalog.csv`:

| Тег SCADA | `device` / `metric` |
|---|---|
| `LT101.Value` | `LT101` / `level` |
| `FT202.Value` | `FT202` / `flow` |
| `P10x.Running` | `P10x` / `running` (0/1) |
| `P10x.Starts` | `P10x` / `starts` |
| `P10x.RunTime` | `P10x` / `run_hours` |

Тревоги: measurement `alarm`, поле `reason` (срабатывание — `Activated`), теги `device` и
`suffix`; приоритет и текст отчёт берёт из `scada_alarms.csv` по коду `<device>.<suffix>`.
Отображение задаётся в `[influx]` и `[influx.metrics]` настроек; каталог можно подать целиком:
`--catalog schema/telemetry_catalog.csv`. Если раскладка точек изменится, правится только файл
настроек.

## Безопасность

- Токен InfluxDB и пароль OPC UA — только из переменных окружения или `.env`; в настройки,
  командную строку и журнал они не попадают. Для отчёта достаточно токена с правом **чтения одного
  бакета**; токен администратора стенда (`INFLUX_ADMIN_TOKEN`) — только для демонстрации, утилита
  предупреждает о нём. Токен на чтение:
  `influx auth create --org vodokanal --read-bucket <ID бакета kns_raw> --description kns-report`,
  затем `INFLUX_TOKEN=...` в окружении службы, которая строит отчёт.
- Адрес `http://` не на локальном узле даёт предупреждение: токен уйдёт открытым текстом.
  В рабочей сети — `https://`.
- Для OPC UA — отдельный пользователь рантайма с правом только чтения и политика
  Basic256Sha256 / Aes128 с режимом SignAndEncrypt. Подробно — [docs/security.md](../docs/security.md).

## Тесты

```bash
python -m pytest report/tests          # сеть не нужна
python -m ruff check report && (cd report && python -m mypy)

# по желанию, на поднятом стенде (make up DEV=1 или make demo DEV=1): запросы Flux к настоящей InfluxDB
set -a; . ./.env; set +a
KNS_REPORT_INFLUX_URL=http://localhost:8086 python -m pytest report/tests -m integration
```

Данные для тестов — в `tests/fixtures/`:

| Файл | Что это |
|---|---|
| `opcua_emulator_recorded.jsonl` | **настоящая запись**: `kns-report opcua --minutes 4 --interval 2` против эмулятора проекта (`emulator/`, модельное время 1:1), 121 опрос, один пуск Н1 |
| `influx_day.csv`, `influx_day_alarms.csv` | **синтетические** сутки в формате ответов InfluxDB 2 на запросы утилиты (annotated CSV) |
| `influx_day_truth.json` | эталон тех же суток по плотной модели (шаг 10 с) |
| `opcua_window.jsonl` | синтетическая выборка «как с OPC UA» 14:13–14:21 (отказ пуска Н2, АВР) |
| `make_fixtures.py` | генератор синтетических данных |

Синтетические сутки — не запись с объекта: `make_fixtures.py` моделирует станцию с шагом 10 с и
публикует теги так, как их публикует ПЛК (по изменению плюс периодически, разрыв передачи
03:20–03:45). Тесты сравнивают отчёт с эталоном плотной модели: объём, моточасы, пуски и тревоги
совпадают точно, уровень — в пределах зоны нечувствительности публикации 0,05 м. По настоящей
записи OPC UA отчёт сверяется с ручным расчётом по тем же строкам, а моточасы — двумя методами
(счётчик ПЛК и время с `Running`). Подмена HTTP и клиента OPC UA проверяет запросы, заголовки,
узлы и обработку сбоев связи.

## Ограничения

- Шаг отчёта — час, пояс по умолчанию — UTC+3 без переходов. Для поясов с переходом времени
  сутки получают 23 или 25 строк.
- Объём — только по расходомеру FT202. При отказе расходомера оценка по характеристике насосов
  не выполняется.
- Полнота считается по уровню и расходу. Разрывы данных насосов и тревог видны только в
  замечаниях к данным.
- Режим OPC UA читает текущие значения и не использует HistoryRead. При потере связи опрос
  пропускает такты, после 10 сбоев подряд останавливается, и отчёт строится по собранным данным.
- Запросы Flux проверены на синтаксис только тестом на поднятом стенде (`-m integration`): на
  машине разработки нет Docker, поэтому без стенда проверяется текст запроса, а не его выполнение.
